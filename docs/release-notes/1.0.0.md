groundwork 1.0 is a local web console for Terraform and Ansible. It's one service on your machine that hosts every infrastructure repository you work on. It checks your code as you edit, shows plans you review and approve before anything is applied, and explains what went wrong when something fails.

## What 1.0 promises

[docs/compatibility.md](https://github.com/rapando/groundwork/blob/main/docs/compatibility.md) lists the surfaces that are now stable, and what a change to each one means for the version number. In short:

- **`groundwork.yaml`, the CLI and its `--json` output** only change in compatible ways until 2.0.
- **A project's `.groundwork/` and the service's data directory** are migrated forward, never down, and backed up first.
- **The HTTP API** is private to the bundled UI. Scripts and agents should use the CLI.

## Upgrading from 0.x

```sh
curl -fsSL https://raw.githubusercontent.com/rapando/groundwork/main/install.sh | sh
groundwork service restart
```

- **Projects:** the first time 1.0 opens a project, it checks the project's `state.db` and copies it to `state.db.bak-<schema>` before migrating it.
- **Configuration:** `groundwork.yaml` needs no changes.
- **From before 0.10:** the console no longer accepts the token in the URL. On your first visit you set up a password, a passkey (Touch ID), or both.
- **From before 0.2:** if you still start groundwork in a terminal, read [upgrading to 0.2](https://github.com/rapando/groundwork/blob/main/docs/install.md#from-01-to-02) first.

## What's in 1.0

### Set up
- Detection of existing Terraform and Ansible code, in a dedicated repository or in a subfolder of an application.
- Scaffold presets for:
  - **AWS**, with S3 state and a lock;
  - **Google Cloud**, with GCS state;
  - **Vultr, DigitalOcean, Hetzner Cloud and Linode**, with local, HTTP or S3-compatible state on each provider's object storage;
  - **Docker**, with a network and a container whose ports you set per environment;
  - **on-prem**.
- The Terraform inventory passes any extra field of the `ansible_hosts` output through as an Ansible host variable, so Terraform can hand Ansible `ansible_user`, `ansible_connection` or your own values.

### Check and edit
- Checks on save, in the editor and in CI (`groundwork check --json`): fmt, validate, tflint, checkov, yamllint, ansible-lint, syntax-check and a built-in secret scanner.
- An editor with inline diagnostics, one-click fixes, bracket closing, indent guides and completion for Terraform and Ansible.

### Plan, approve, apply
- A plan screen that flags dangerous changes (destroys, replacements, your own `terraform.danger` patterns) and asks for a typed confirmation where it matters.
- Approval of the exact plan for production-like environments.
- Ansible dry runs reviewed like plans.
- A run screen with live logs and a per-host, per-task grid.
- Runs have a timeout. They are stopped gracefully, so terraform releases its state lock. After a hard stop, groundwork reports any tools it left running.

### Understand
- The Graph screen, with a System view that places Ansible hosts, roles and ports on the Terraform servers they run on.
- Drift checks, on demand or on a schedule.
- Doctor, which checks:
  - tools and their versions;
  - credentials for AWS, Google Cloud, Azure, Vultr, DigitalOcean, Hetzner and Linode, and the Docker daemon;
  - state backends, including S3-compatible ones, and their locking;
  - the SSH agent, inventories and vault passwords.

### Security
- The console signs in with a password or a passkey.
- The service binds to loopback only and checks the Host and Origin of every request.
- Secrets and `sensitive` values are redacted everywhere a tool might echo them.
- `groundwork.yaml` values that reach tools are validated.
- Releases are signed with cosign and come with an SBOM per archive.

### Operate
- One service per data directory, started at login with `groundwork service install`.
- A rotated log, `groundwork service logs -f`, and a `service status` that shows what the service is doing.
- A crash in one project's background work is contained to that project and reported as an issue.

### For agents
- [`skills/groundwork`](https://github.com/rapando/groundwork/tree/main/skills/groundwork) is an [agent skill](https://agentskills.io) that teaches coding agents (Claude Code and other skill-aware agents) to use the CLI: validate with `check --json`, diagnose with `doctor --json`, check drift and scaffold. They hand plans and applies to you in the console instead of applying anything themselves.

## Known limitations

- **Platforms:** macOS and Linux only (amd64 and arm64).
- **Locks are in-process:** a `terraform` you run in your own terminal isn't coordinated with the service.
- **The HTTP API isn't a public surface.** Scripts should use the CLI: `groundwork check --json`, `groundwork doctor --json`, `groundwork projects`.
- **State locking on S3-compatible storage:** on Vultr, DigitalOcean and Linode, `use_lockfile` stays commented out until you've confirmed the storage supports conditional writes.
- **Installing:** there's no Homebrew tap; use the install script or `go install`.
